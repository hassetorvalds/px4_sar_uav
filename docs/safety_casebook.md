# 安全分层案例集（把"踩过的坑"固定成准入案例）

> 服务器侧 2026-10-16 建议：把几次真实事故/险情整理成案例，作为**安全层变更的准入门槛**。
> 每条都给出：现象 → 根因 → 修法 → 证据（有飞行取证的注明 session/文件）。

## 案例 1：位置点式转场 → **高速撞障碍**

```text
现象：用户现场看到多次"以高速撞上障碍物"。
根因：转场（TRANSIT/DESCEND）直接发**最终位置目标点**，PX4 用自己的巡航速度执行
      （MPC_XY_CRUISE≈3 m/s、上限 12 m/s），路径中间隔着建筑就是高速撞击。
证据：d9 CSV t=25.8→26.3 s 局部坐标跳 36 m（位置阶跃签名）。
修法：转场改**速度控制**（transit_speed_mps 精确限幅）+ **前方净空硬停**（transit_stop_clearance_m）。
      注意"位置追踪点"不是解：实测只有 0.11 m/s（98 s 走 11 m），到不了目标。
通则：**规划层给目标，执行层必须自己限速 + 净空硬停**。
```

## 案例 2：**传感器盲区仍在推进** → 贴近/疑似接触障碍

```text
现象：净空读数在 0.45 m 处"触底"（= min_range 过滤值）后仍在 creep 前进。
根因：`0.45` 的含义是"**≤0.45，未知**"，不是"还有 0.45 m 余量"；保持态 creep 仍以 0.05 m/s 前推。
修法：**盲区底线**（`obstacle_blind_zone_m=0.5`）——净空 ≤0.5 m 时**前向一律归零**（含 creep 与前向下限），
      保留偏航；并把"是否触底"落盘为 `at_min_range`（不把触底值当真值）。
通则：**引入任何"让他继续前进"的改动前，先问"传感器在更近处还能不能看见"**。
```

## 案例 3：**转角封顶却在硬推**（自由度被限制，耦合动作没限制）

```text
现象：k7-e2 贴在大结构上（簇 3000–4000 体素）、右侧本来是 inf（可绕），却始终没绕开。
根因：`yaw_capped=True`（累积转角 ≥60°）把偏航置 0（防原地打转），**但 creep 仍以 0.05 m/s 前推**
      → "既不转、又继续推" → 贴死。
证据：该段 turn_deg 64–69°、yaw_capped 16/18 帧、creep 0.05 持续。
修法：封顶时**前向也归零**（只停不推，交脱困/预算/超时兜底）。
验证：修复后 193 个 yaw_capped 帧里"前向>0"的 = **0**（唯一非零是脱困后退 −0.1 m/s）。
通则：**当某个自由度被限制时，与之耦合的推进必须一并限制**。
```

## 案例 4：**"持续不可绕"下的最外层兜底**（安全链端到端）

```text
场景：注入"两侧持续都紧、永不解除"（`escape_hold`），驱动 RUN_S 设大不让它先收工。
时间线（sup2 s1016-200910，每步有日志）：
  保持>20 s → 脱困×2（0.92 / 0.91 m，各有界 ~9 s）→ 重试用尽「不再后退」(ERROR)
  → 驱动保持悬停（**前向恒 0**）→ **监督层「RUN 151 s > 150 s → land_fast」** → 安全落地
意义：**机载 → 驱动 → 监督层 → 全局** 四环在"持续不可绕"下首次端到端走通，且**不硬推**。
```

## 案例 5：**"落地后终端仍 running"**（进程生命周期 vs 指标）

```text
现象：飞机早已落地，终端/脚本一直 running。
根因：① 监督层按阶段预算下发 land_fast，**驱动不知道**，继续跑自己的阶段机；
      ② SCAN 发现候选 → ROTVERIFY 失败 → 回 SCAN 时 `enter()` 重置了 SCAN 计时 → `scan_max_s` 永不
         到期 → 死循环。
修法：① 驱动加安全闸"曾解锁 → 现在上锁 ⇒ 立即收工退出"；② SCAN 计时绑定"本点扫描起点"，
      复验失败返回时不重置；③ 脚本 `timeout 900` 兜底。
通则：**超时必须严格嵌套（内层 < 外层）**：机载 < 驱动 < 监督层 < 全局。
```

## 附：其它已固定的纪律

```text
· 单组 VLM 节点：起飞前按 PID 清陈旧节点（多栈会互相抢推理槽/抢爬升）；
· 每轮全新 session_id；preflight.sh fail-closed（各 1 + /fmu/out + 地图 frames>0 + 远端 /health）；
· 不调用 AirSim reset()（会断 lockstep）；重启 PX4 ≠ 把飞机搬回世界出生点（只重设本地原点）；
· 窗口类判据必须 ≥ 对应的时间预算（例：闭合窗口 ≥ 保持+脱困；20 帧 ≈9 s < 20 s+10 s ≈44+22 帧）。
```

## 案例 6：同域跑假 PX4 自检 → 真机被误 arm（2026-10-18）

```text
现象：真实栈在线（PX4 + offboard_bridge），另起 task_executor_simcheck.sh；
      自检执行器把 arm/offboard 发到共享 /offboard_bridge/command，真实 bridge 转发给真 PX4；
      真机 arming_state=2、nav_state=14，AirSim z=-1.77（约 1.8 m 高）。
根因：假 PX4 与真栈共用 ROS 域和话题；自检没有检查真实链路是否在跑；
      bridge 对命令来源没有隔离（它只认话题，不认进程）。
修法：simcheck 启动前检查 px4/offboard_bridge，默认拒绝（exit 2）；
      SIMCHECK_ALLOW_LIVE=1 仅显式覆盖。
处置：kill 假 PX4/自检执行器 → 发 /offboard_bridge/command land_fast
      → 8 s 后 arming_state=1、landed=true、AirSim z≈-0.06；无碰撞/无损伤。
通则：任何"假飞行器/回放/自检"必须与真实控制链路隔离
      （不同 ROS_DOMAIN_ID，或显式互锁）；共享话题的半实物测试默认拒绝。
```
