结论：**不排队、无显存泄漏**；+2.7GB 是真实 1280×720 推理首次分配后一次性抬高，之后稳定。

## 关于指向贴底边：我的判断（回答你的三问）

**核心事实**：README 明确定义了两路输出——
- `apos` = **affordance / 自由空间落点**（"a feasible local direction or free-space waypoint"）
- `opos` = **目标物体**

所以 `apos` **本来就不是目标物体**，而是"往哪走"的可通行落点。它落在画面底边中心 + `clamped=true`，含义是**"前方地面、正前方"**——这是模型在说"**向前走**"，是预期行为，不是 bug。

**你看到的"下降 −0.51 m/s"是你们自己的反投影产物**：把底边的地面点做几何反投影成三维目标，再算机体速度，自然带向下分量。地面机器人这样算就是"前进"；无人机不能这么用。

**一个强证据**：我在服务器侧用**完全不同的 480×270 合成帧**测试时，`apos` 归一化坐标也是**一模一样的 0.5104 / 0.9815（grid id 1273，底边中心）**。跨两种分辨率、两种内容都恒等 → 说明这是模型的**默认"向前"落点单元**，不是你们场景的伪影。

逐条回答：
1. **正常输入下 apos 落在哪？** —— 就是画面下方（地面落点），底边中心即"正前方"。因此"贴底边 + clamped"是**预期**，不是异常。
2. **指令写法** —— 目标要是场景里**真实存在且显著**的物体；户外优先 `turn left/right`；`collapsed building` 很可能是**未见类别**，且你的场景没有它，所以 `opos` 一直 `not_visible`（对象通道没接上）。示例：`Turn left and go to the red vehicle ahead`、`Go to the building on your right`。
3. **是否按"地面目标"处理？** —— 可以，但要**按自由空间处理，不要做 3D 反投影**：只取它的**水平方位（x）**和"向前"语义，**高度交给飞控保持**，绝不据此生成垂直速度。

**三种可能里，主因是 #1（语义理解差异：apos 是落点不是目标），叠加 #2（目标未见 → opos 失效）。#3 采样率是次要因素**——而且你全程悬停、场景静止，"向前"输出恒定本来就是自洽的，不能据此判断模型坏了。
