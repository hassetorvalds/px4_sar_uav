## 三、Step C 意见

**总体同意 C1→C2→C3 的分步，尤其第一轮"只偏航、不加前进"是对的** ——
先隔离并验证 yaw 链路，是最安全的最小闭环。两点具体建议：

**1. ⚠️ 方向风险（C1 要重点验证的）**
PX4/MAVROS 的 body yaw rate 是 **FRD 机体坐标系、顺时针（右转）为正**；
而 LightNav 的 `yaw` 是 **逆时针（左转）为正**。两者**符号相反**——
映射到 PX4 时**很可能需要取负**。判据很直观：`rot_left`（`yaw=+0.314`）应让机头**左转**；
若实际右转，就是符号反了，立刻停。C1 正好能一次性验证方向与幅值。

**2. C1 安全包络建议**
- 偏航角速度先**限到较小值**（如 ≤0.5 rad/s）而不是直接饱和到平台上限，方便观察且安全；
- watchdog：无响应 / 5xx / `stop` / `not_visible` → 角速度**归零保持**；
- 地理围栏 + 硬性时间上限（如 30 s 到点自动悬停）。

**3. C2**：同意加前进分量，但建议**从低速起步**（0.3–0.5 m/s，而非直接 1 m/s），确认不发散再提速。

**4. C3**：同意把本机局部地图/避障层接进 VLM 指令通道；这一步之后 VLM 才真正"看得见阻挡"。

## 四、更正：关于"实时喊停"（重要）

我上一封信里说"有排队或显存增长我会立刻喊停"，**这句话不准确，在此更正**：

- 我这边是**被动的**。后台监控脚本只把 `GPU 显存 / 利用率 / 请求数 / 最近延迟` **写进日志文件**，
  它**不会**主动通知任何人，也**不会**打断你们的飞行。
- 我本人也**无法实时介入**——我只在你们下次沟通时才能读日志、看现象。这个回路是**分钟级甚至更慢**，
  **不构成任何安全机制**。请把我看作"记录员 + 事后分析"，**不要当作实时急停**。
- **实时安全必须放在你们机载侧**（这是唯一够快的回路）。请确认客户端具备：
  - 请求超时 / 连续错误 N 次 → **速度归零并悬停**（或降落）；
  - 服务端延迟超阈值 → 降级为"锁存上一指令 / 保持"；
  - 保留你们已加的 `ConnectionReset` 跳过重试与"禁止持续下降"。
- 服务端我**能**做的（可选，需你们明确同意）：把监控改造成**主动看门狗**——超过阈值就写告警文件，
  或（更激进）**自动停掉服务**，让客户端连接失败从而触发你们机载的失效保护。
  但"自动停服务"会造成非预期断连，**默认不做**，要你们说了才加。

**结论**：急停是你们机载 watchdog 的职责；服务端只提供数据。

## 五、看门狗方案（供你们选择；默认 W3 不做）

背景见第四节：**实时急停必须由机载 watchdog 负责**。服务端能做的是"提供更细的遥测"和
"过载时快速失败"，让你们的机载 watchdog 有依据、且能及时触发。三个层次，从安全到激进：

**方案 W1（只读遥测 + 告警文件）—— 推荐，无风险**
- 把 `/health` 扩展为轻量遥测端点（仍同步、不跑推理，可高频轮询）：
  ```json
  {"ready":true,"sessions":N,
   "gpu_mem_mib":14280,"gpu_mem_free_mib":...,"gpu_util_pct":...,
   "inflight":0,"recent_p95_ms":251,"recent_max_ms":517,
   "frames_total":746,"uptime_s":...}
  ```
- 后台监控脚本额外：超阈值就向 `watchdog.alert` 追加一行告警（时间 + 指标 + 数值）。
- 你们可让客户端**低频轮询** `/health`（如 1 Hz），或经 SSH 读告警文件。
- 阈值示例（可调）：显存较基线增长 > 4 GiB；`recent_p95_ms` > 800；`inflight` > 1 持续 > 5 s。
- 特点：只增加信息，**不改变任何行为、不断连**。

**方案 W2（过载快速失败）—— 中等，需你们确认**
- 当 `inflight` 超过 `max_batch`（当前 = 1，即同一时刻只有一帧在推理）时，**不再排队**，
  直接对多余请求返回 **`503`**。
- 效果：过载时客户端**立刻拿到失败**，由你们机载 watchdog 决定"保持/悬停"，
  而不是静默排队导致延迟悄悄飙升。
- 你们当前负载（~2 Hz、单客户端）正常情况**永远不会触发**，只在异常并发时生效。
- 需要你们客户端把 `503` 与超时同样处理（你们已有超时/重试逻辑即可）。

**方案 W3（自动停服务 / fail-safe）—— 激进，默认不做**
- 看门狗持续超阈值时**主动关闭 `server_http.py`**，让客户端连接被拒 → 触发机载失效保护。
- 风险高：会造成非预期断连；若客户端当时未正确进入"保持/降落"，反而更危险。
- 只有你们明确要求、并确认机载侧对"连接失败"的处理后，才会加。

**建议**：做 **W1 + W2**（W1 给轮询依据，W2 保证过载时快速失败而非静默排队）；**W3 不做**。
请回：① 是否要 W1 / W2；② 若做，阈值与轮询频率用上面默认还是你们指定。
